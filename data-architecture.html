n8n או שרת? חשיבה מחודשת לאור התראות מותאמות אישית

כשנכס חדש עולה ומתאים ללקוח לפי ההכנסה, ההון העצמי, הבנק, ההטבות במס וכו', הלקוח מקבל התראה. הדרישה הזו משנה איפה הלוגיקה צריכה לשבת.

Nadlan Score טיוטה v2 · 2026-10-05 משלים את spec.md §4.1, §4.5, §5, §8, §9

1השורה התחתונה

עדכון v2.1 (2026-10-05): החלטות של בעלי המוצר
  • SMS ו־WhatsApp נשלחים דרך n8n עם Twilio. n8n מקבל תפקיד שני, "צינור יציאה": הוא רק לוקח הודעות מוכנות מהשרת ושולח. ההחלטה למי, מתי ומה נשארת בשרת. ההודעות לא כוללות דאטה פיננסי אישי. הפירוט ב־backend-spec.md §6.4.
  • אין גלישה בלי חשבון. כל מסך, כולל המפה, דורש כניסה עם OTP בטלפון.
ההמלצה נשארת היברידית, אבל הגבול זז: השרת הופך ללב המערכת, ו־n8n נשאר "צינור כניסה" בלבד.
  • n8n: מושך ומנקה דאטה ממקורות חיצוניים (מודעות, עסקאות, תוכניות, ריביות) וכותב ל־Postgres. הוא לא קורא פרופילים ולא מחליט למי לשלוח התראה. v2.1 הוא גם שולח SMS ו־WhatsApp דרך Twilio, אבל רק הודעות שהשרת כבר הכין.
  • השרת (Supabase): מחזיק את פרופיל הלקוח. ברגע שנכס חדש נכנס ל־DB, השרת מחשב ציון, מוצא לקוחות מתאימים, בודק לכל אחד יכולת מימון אמיתית (הון עצמי, LTV, החזר מול הכנסה, מס רכישה) ושולח פוש.
  • מנוע אחד, שלושה מקומות: אותן פונקציות טהורות (lib/mortgage, lib/tax, lib/match, lib/score) רצות באפליקציה, ב־Edge Functions ובטסטים. אם ההתראה אומרת "אתה יכול לקנות את זה בהחזר של 6,200 ₪", המחשבון באפליקציה חייב להראות את אותו מספר.

למה זה מחזק את ההמלצה הקודמת ולא הופך אותה: התאמה אישית היא בדיוק לוגיקה עסקית. היא נשענת על דאטה פיננסי רגיש, צריכה טסטים, וחייבת להיות עקבית עם מסך המשכנתא. אסור שהיא תשב ב־workflow. מה שכן השתנה: הפרופיל לא יכול לחיות רק במכשיר, והמערכת עוברת מ"עדכון מתוזמן" ל"תגובה לאירוע".

3האפשרויות מחדש

א. n8n עושה גם את ההתאמה וההתראות

לא מומלץ

n8n מושך נכס חדש, טוען את כל המשתמשים, מחשב לכל אחד התאמה ב־Code node ושולח פוש.

+ מהיר לדמו. n8n טוב בשליחת הודעות (מייל, טלגרם, WhatsApp).

− דאטה פיננסי של כל הלקוחות עובר דרך n8n ונשמר ב־execution logs. זה סיכון פרטיות ממשי.
− עותק שני של מתמטיקת המשכנתא, שיתרחק מהאפליקציה. בסוף הלקוח יקבל התראה שסותרת את המחשבון.
− N נכסים × M משתמשים בלולאה של JS לא סקיילבילי.
− אין טסטים, ואין דרך טובה להסביר "למה קיבלתי את ההתראה הזו".

ב. n8n מתאים, השרת מחשב

פשרה גרועה

n8n מתזמר: קורא לשרת "תחשב affordability למשתמש X ולנכס Y" ושולח את ההתראה לפי התשובה.

+ החישוב עצמו נשאר בקוד.

− אלפי קריאות HTTP לכל נכס חדש.
− n8n עדיין צריך לדעת מי המשתמשים ולהחזיק push tokens.
− הלוגיקה של "למי שולחים, מתי, כמה פעמים" מתפצלת בין שני מקומות.

ג. n8n = כניסה, שרת = מוח (מומלץ)

מומלץפרטיותעקביות

n8n כותב נכס ל־DB, ומכאן הכול קורה בשרת: Trigger מכניס job לתור, Edge Function מחשבת ציון והתאמות, נכתבת רשומת התראה לטבלת outbox, ו־dispatcher שולח פוש דרך Expo Push.

+ n8n לא רואה אף פעם דאטה של משתמש.
+ מנוע אחד משותף לאפליקציה ולשרת.
+ סינון מוקדם ב־SQL עם אינדקסים, כך שרק מאות מועמדים עוברים חישוב מלא.
+ כל התראה שומרת "למה" (reasons), וזה מוצג ללקוח ומשמש ל־debug.

− יותר קוד שרת ממה שתכננו ב־v1, ופרופיל וחשבון נדרשים מוקדם יותר.

ד. התאמה במכשיר (Background Fetch)

לא עובד

האפליקציה בודקת ברקע אם יש נכסים חדשים ומחשבת התאמה מקומית, כך שהפרופיל לא עוזב את המכשיר.

+ פרטיות מקסימלית.

− iOS לא מבטיח ריצה ברקע. ההתראות יגיעו באיחור של שעות או לא יגיעו.
− אין "התראה ראשונה" על נכס חם, ובזה בדיוק כל הערך.
− אי אפשר לנתח המרות או לנתב לידים ליועצים.

6מנוע ההתאמה

שני שלבים, כדי שלא נחשב משכנתא מלאה לכל משתמש על כל נכס:

שלב 1: סינון מוקדם ב־SQL (מהיר, עם אינדקסים)

select u.user_id
from buyer_derived u
join alert_preferences p using (user_id)
where p.enabled
  and :city = any(p.cities)                      -- or ST_DWithin on a drawn area
  and :rooms between p.rooms_min and p.rooms_max
  and :price <= u.max_price * 1.05              -- small tolerance; precise check is next
  and coalesce(:score, 0) >= p.min_score

שלב 2: התאמה מלאה (TypeScript, אותו קוד כמו באפליקציה)

// lib/match/index.ts — pure, shared by app + edge function + tests
export function evaluateMatch(
  profile: BuyerProfile,
  property: Property,
  ctx: { rates: MortgageRates; regulation: RegulationConfig; taxBrackets: TaxBrackets; score?: PotentialScore }
): MatchResult

type MatchResult = {
  eligible: boolean;
  purchaseTax: number;          // lib/tax, by buyerType (first home vs. upgrader vs. investor)
  totalCashNeeded: number;      // down payment + tax + lawyer + agent + buffer
  equityGap: number;            // negative = has spare equity
  loanAmount: number;
  ltv: number;                  // vs. regulation.maxLtv[buyerType]
  monthlyPayment: number;       // lib/mortgage, "balanced" plan
  paymentToIncome: number;      // vs. 50% max / ~33% recommended
  reasons: LocalizedText[];     // "המס שלך כדירה יחידה: 0 ₪", "החזר משוער 31% מההכנסה"
};

7מנכס חדש ועד פוש

  1. n8n מושך פיד של שותף, מנרמל, עושה geocoding ו־upsert ל־properties.
  2. DB Trigger על insert (או על ירידת מחיר) מכניס הודעה לתור property_events. n8n לא צריך לקרוא לשום דבר.
  3. Worker: score אוסף inputs ב־PostGIS, מריץ computeScore ושומר ל־property_scores.
  4. Worker: match מריץ סינון מוקדם (שלב 1) ואז evaluateMatch לכל מועמד (שלב 2), ושומר ל־matches.
  5. לכל התאמה שעברה נכתבת שורה ל־notification_outbox, או שההתאמה נצברת ל־digest לפי העדפת המשתמש.
  6. Dispatcher (pg_cron כל דקה) בודק שעות שקט, שבת וחג ומגבלה יומית, שולח דרך Expo Push API ומעדכן receipts. טוקנים לא תקינים נמחקים.
  7. המשתמש לוחץ ונכנס ל־property/[id], ושם כרטיס "למה זה מתאים לך" מציג את ה־reasons ואת אותם מספרים מהמחשבון.

8כללי התראות

  • Opt-in מפורש לכל סוג התראה, עם ברירת מחדל שמרנית.
  • מגבלה יומית לכל ערוץ, שהמשתמש יכול לשנות: פוש עד 5 ביום, ו־SMS, WhatsApp ומייל כסיכום יומי כברירת מחדל. מה שמעבר למגבלה עובר ל־digest. הפירוט ב־backend-spec.md §9.3.
  • שעות שקט: 22:00–08:00 כברירת מחדל, ובלי שליחה בשבת ובחגים (ניתן להגדרה).
  • Dedupe: מפתח ייחודי (user_id, property_id, event_type), כך שלא מתריעים פעמיים על אותו נכס.
  • כל התראה כוללת "למה", ויש קישור "פחות כאלה" שמעדכן את ההעדפות.
  • שפה: הטקסט נבנה בשרת לפי locale של המשתמש (he/en).

9פרטיות ואבטחה

זה השינוי הכי משמעותי עד עכשיו הנתונים הפיננסיים יכלו להישאר במכשיר. מרגע שיש התראות מותאמות, הכנסה, הון עצמי, בנק ודירוג אשראי יושבים בשרת. זה דאטה רגיש לפי חוק הגנת הפרטיות (כולל תיקון 13). יש לאמת את הדרישות מול עורך דין לפני השקה.
  • הסכמה נפרדת ל"שמירת הפרופיל בשרת לצורך התראות". בלי הסכמה, הכול נשאר מקומי ואין התראות מותאמות (רק התראות לפי פילטרים).
  • RLS על כל טבלאות המשתמש. ה־workers רצים עם הרשאות מינימליות.
  • n8n לא מקבל גישה לטבלאות משתמשים בכלל, ברמת הרשאות ה־DB. v2.1 בשליחה הוא מקבל רק טלפון וטקסט מוכן, בלי דאטה פיננסי אישי, דרך פונקציות delivery.*.
  • מינימום דאטה: לא צריך שמות או גילאים להתאמה. שומרים רק את מה שנכנס לחישוב.
  • מחיקה וייצוא (spec §4.7) חלים גם על matches ועל ה־outbox.
  • חוק הספאם (חוק התקשורת, סעיף 30א): פוש עם CTA ליועץ עלול להיחשב דבר פרסומת בערוצים כמו מייל, SMS ו־WhatsApp. נדרש opt-in מתועד.
